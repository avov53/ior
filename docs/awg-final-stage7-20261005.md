# AWG: последняя итерация, stage7, 5 октября 2026

Статус: кандидат для ручного сравнения. Ускорение YouTube, сайтов и приложений
пока не подтверждено. Изменения устраняют конкретное ограничение клиентского
пакетного пути; они не гарантируют пропускную способность внешнего сервера/CDN.

## Изменения

- Пакетный TCP-путь AWG принимает до 128 активных соединений вместо 24.
  Соединение с FIN только с одной стороны остаётся активным. После FIN с обеих
  сторон или RST оно перестаёт занимать место для нового активного соединения.
- Закрывающиеся соединения сохраняются для поздних ACK/FIN до 120 секунд.
  При проверке допуска/обслуживании остаётся не более 128 закрывающихся
  соединений; старейшие излишние записи освобождаются. После освобождения
  ограниченная таблица удерживает принадлежность поздних пакетов пакетному
  пути ещё 120 секунд: они поглощаются, а не передаются другому TCP-стеку.
  Свежий SYN с повторно использованной парой адресов может открыть новое
  соединение. Наблюдаемые соединения прежнего пути остаются на прежнем пути.
- Для сохраняемых пакетов raw TCP введён общий бюджет 64 МиБ на AWG-сессию
  для обоих направлений. Разрешение резервируется до копирования данных и
  передаётся вместе с пакетом через очереди транспорта и записи в TUN.
  Чтение из очереди само по себе не освобождает бюджет: пакет может ещё ждать
  записи. Отмена, ошибка, закрытие и удаление очереди освобождают разрешения.
- В бюджет входит запас 40 байт для перевода IPv4 ICMP с цитатой в IPv6 ICMP:
  расширяются и внешний заголовок, и заголовок цитируемого пакета. При
  переполнении очереди/бюджета пакеты отбрасываются с агрегированной
  диагностикой; действующее TCP-соединение не переключается между стеками.
- `AWG_RAW_TCP_METRICS` теперь показывает active/closing/retired, лимиты,
  объёмы и число пакетов. `AWG_RAW_TCP_FALLBACK_METRICS` агрегирует причины
  использования прежнего пути. `AWG_RAW_PACKET_METRICS` показывает текущую
  и максимальную наблюдённую резервацию, отказ бюджета и переполнение очередей.
  Форматтер приложения сохраняет эти поля, а также выбранный адрес при
  переводе IPv6 в IPv4. Содержимое пакетов и ключи не журналируются.

Бюджет 64 МиБ относится к сохраняемым пакетам raw TCP, не ко всей памяти
процесса. Существующий отдельный бюджет буферов smoltcp, фиксированные
буферы драйвера/сборки фрагментов, кратковременные преобразования и буферы
Windows TCP считаются отдельно.

Официальный Go-движок, pipe framing, MTU, профиль, ключи, сервер и DNS не
менялись. DIRECT/REJECT и соединения, которым нужен анализ имени из TLS,
сохраняют прежние правила маршрутизации. Windows IPv6 не отключается.

## Пакеты и проверки

Контроль: копия фактического `dist/windows-11` перед изменениями в
`verification-publish/20261005-awg-final-stage7/control-windows-11`.
Хеши `ior.dll` и ядра записаны в `control-hashes.json`. Старые пакеты сохранены.
Новый кандидат: `verification-publish/20261005-awg-final-stage7/windows-11`.
`dist.bat` не запускался. Итоговые проверки и хеши находятся в `build-result.json`.

Стенд общего менеджера проверяет 128 одновременно открытых и 300
последовательных TCP-соединений через реальный официальный Go AWG-движок
при заданной локальной задержке 50 мс: эхо должно совпадать, fallback из-за
ёмкости не допускается, разрешения памяти/потоки освобождаются после отмены.
Таблицы закрытия и поздние ACK/повторный SYN проверены отдельно.

Стенд передачи проверяет задержки 50/100/200 мс и фиксированные потери
0/0,5/1%, маленькие запросы, upload, параллельные download, медленного читателя,
отмену и повторную загрузку. Основной набор также проверяет целостность
64 МиБ и IPv4/перевод IPv6. Результаты находятся в JSON и журналах пакета.
TCP-участники этих стендов синтетические: это проверка корректности, а не
измерение скорости настоящего Windows TCP или YouTube.

Тест с настоящим Windows TCP и собственным Wintun требует администратора и
в этой итерации не запускался. Автоматизация Firefox не использовалась.

## Последнее ручное сравнение

1. Закрыть другой экземпляр ior полностью, затем включить AWG + ior-core + TUN
   в контрольном пакете. На телефоне отключить VPN с тем же конфигом на время
   сравнения. Сохранить обычные DNS/DoH и одинаковые правила маршрутизации.
2. Выполнить пять повторов Telegram Web, одной страницы YouTube и одного
   видео в фиксированном 4K: запуск, перемотка к одинаковому месту, скорость
   2×. Разделять первый заход и повторный. Записывать время первого кадра,
   число/длительность остановок и запас буфера из «Статистики для сисадминов».
3. Повторить на кандидате с теми же условиями, по возможности чередуя
   контроль и кандидат. Пинг измерять отдельно к одному адресу одним методом.
4. Только после этого отдельно сравнить новый пакет с временно выключенным
   Firefox DoH и полностью перезапущенным браузером. DNS приложения/профиля
   оставить прежним. Сохранить и затем вернуть исходную настройку DoH.
5. Вместе с результатами сохранить журнал: важны active/closing,
   FALLBACK_METRICS, RAW_PACKET_METRICS, RAW_TCP_TRANSLATED/FIRST_DATA и
   прежние TUN_TCP/TUNNEL_TCP_SOCKET_METRICS. TCP-путь конкретного видео
   нельзя установить по одному общему счётчику; сопоставлять потоки/адреса
   браузера с журналом, не предполагать автоматически, что видео использует h3.

Принятие: повторяемое уменьшение времени запуска/остановок без роста ошибок.
Если преимуществ нет или результат неоднозначен, ускорение остаётся
неподтверждённым; возвращаем лучший стабильный пакет и прекращаем эту серию
оптимизаций, как согласовано с пользователем.
