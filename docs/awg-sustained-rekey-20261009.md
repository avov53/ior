# AWG: замедление спустя две минуты — диагностический кандидат

## Сохранённые контроли

- stable-fast-control.zip: полный ранее принятый быстрый пакет, с точными отличиями
  Windows 10 в windows-10-overrides. Ядро efbf6c928fbadb0bffec38949c4a61cfafb13be556b9079f50a56a65fcdc6ef3.
- seek-fast-control-overlay.zip: компактные файлы последнего улучшенного кандидата
  до этой работы, ядро 455b2b3187c26cb0ae5134c11058c303f428b42dd4271898444ea921641224c2.
  Для его восстановления сначала распаковать полный stable-fast-control, затем
  overlay поверх него. На Windows 10 также применить windows-10-overrides.
  APPDATA/профили архивами не заменяются. Оба контроля сохранены отдельно от кандидата.
- При заданном вручную внешнем пути ядра убедиться, что используется ядро выбранного
  пакета: его SHA256 указан выше. Архивы не перезаписывались при упаковке кандидата.

## Что проверено

Один локальный сценарий одновременно сравнил Rust и официальный Go с синтетическими
ключами: RTT 100 мс, фиксированные потери 0,5%, штатные сроки ключей 120/180 с.
По 22 проверки сохраняемых TCP/UDP-потоков раз в 10 с; шесть новых загрузок 1 МиБ
с целостностью до/после rekey; две отмены загрузки 2 МиБ после получения начала.
Длительность: Rust 211,606 с, Go 212,335 с. Зависаний/потери целостности не было.
У Rust зафиксировано реальное обновление сессии: generation 1 → 2, rekey 123 мс.
Медиана TCP+UDP-запросов Rust 245 мс, Go 248 мс; p95 250/251 мс, максимум 251/252 мс.
Новые загрузки колебались примерно 1,2–2,0 с у обоих движков, без устойчивого
ухудшения после двух минут. Этот стенд не воспроизвёл задержку перемотки Firefox.
Он не использует TCP Windows/Wintun и не определяет поведение внешнего сервера/CDN.

17 целевых AWG-тестов, 5 DNS-кеша, 12 DNS TUN и 2 .NET-проверки экспорта диагностики
прошли; группы Rust пересекаются, их числа не складываются в уникальный набор.
Release Rust и self-contained Windows 10/11 publish прошли. Локальная длительная
проверка выполнена на Windows 11; живая Windows 10 требует отдельного сравнения.

## Изменения

Подтверждённого дефекта передачи нет, поэтому исправления производительности не
включены. Rust по умолчанию, окно 512 КиБ, бюджет 64 МиБ, маршруты, DNS/TTL, MTU,
ключи, обфускация и выбор таймингов сохранены. Циклического переподключения и
искусственного продления TTL нет.

Добавлена только наблюдаемость:

- AWG_REKEY_STARTED / AWG_REKEY_COMPLETE и AWG_HANDSHAKE_RETRY: порядковый номер
  поколения, попытка и длительность. Read-only метод локальной копии BoringTun
  читает существующее состояние; криптографические переходы не изменялись.
  Реальные индексы сессий и ключи в журнал не выводятся.
- AWG_SESSION_PROGRESS раз в 10 с: возраст ключа, pending handshake, полученные
  IP-байты и время последнего принятого IP-пакета. Это не время кадра видео.
- AWG_DNS_CACHE_LOOKUP: missing или expired; AWG_DNS_SHARED_CACHE_HIT — попадание.
  expired определяется, если соответствующая истёкшая запись ещё была в таблице
  при проверке; после удаления/вытеснения результат missing не доказывает причину.
- Новые поля передаются в журнал приложения и диагностический экспорт C#.
  Сохранены ограничения безопасных полей и псевдонимизация адресов при экспорте.

## Следующая ручная проверка

Запускать весь каталог awg-current/windows-11 или windows-10. На одном видео 4K,
с одинаковыми DNS/сервером/маршрутом: перемотка сразу, спустя 2 и 5 минут, затем 2×.
При замедлении записать точное время, Buffer Health/Dropped Frames и журнал:
нужно сопоставить rekey, DNS miss/TTL, смену CDN/адреса и прогресс нужного потока.
Если кандидат ухудшил результат, использовать сохранённый контроль.

Статус: пользовательское замедление после двух минут не исправлено и локально не
воспроизведено; выдан диагностический кандидат. Ускорение/отсутствие регрессии в
браузере не заявляется. Firefox не автоматизировался; пользовательский сервер и
системные маршруты проверками не менялись. Промежуточные файлы/кеши этой работы
очищены, короткие результаты и контрольные суммы сохранены в validation.json.
