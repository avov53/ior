# AWG: TCP и DNS, вторая итерация, 2026-10-04

Статус пользовательской скорости: **ускорение сайтов и видео не подтверждено**. Проверки ниже относятся к локальному стенду и корректности клиента. Браузер, первый кадр и перемотку проверяет пользователь.

Контрольный пакет: `verification-publish/20261004-awg-poll-stage1/windows-11/ior.exe`. Новый self-contained Windows x64 пакет собран в `verification-publish/20261004-awg-tcp-dns-stage2/windows-11/ior.exe`.

## Изменения основного кандидата

- Nagle отключён только на исходящих TCP-сокетах AWG в ior-core. ACK delay сохранён. Локальный TCP-участок TUN сохраняет прежние Nagle, ACK delay и алгоритм None; WireGuard и остальные протоколы не получают настройки AWG.
- Исправлен half-close: FIN не прекращает отправку. Буфер отправки и FIN/ACK завершаются корректно; завершённая задача чтения повторно не опрашивается. Удаление всего stream отменяет поток и освобождает бюджет, а `shutdown` одной половины сохраняет другую. Регрессия на официальном AWG до исправления давала `BrokenPipe`; после исправления WG и AWG принимают данные после EOF.
- Добавлено необязательное состояние `AwgDnsOverride` (`null` по умолчанию). Приоритет: override AWG → DNS импортированного профиля → общий DNS. Исходный профиль не переписывается.
- В настройках DNS появились варианты «Из профиля», Google + Cloudflare (`8.8.8.8, 1.1.1.1`) и пользовательский список 1–4 IP-адресов. Сохранение проверяет IP-адреса; для выбранного AWG проверяются также локальная семья адресов и AllowedIPs. Контракт повторно проверяет настройки до сетевых изменений.
- Резервная DNS-проба AWG запускается через 150 мс вместо 500 мс; при явной ошибке — сразу. Проигравшая операция отменяется, её UDP relay не возвращается в пул с чужим ответом. DIRECT и остальные протоколы сохраняют 500 мс.
- TCP- и UDP-подключения по имени используют общий DNS-путь. Кеш TUN DNS разделён по resolver, маршруту, UDP/TCP и параметрам запроса; новое подключение создаёт кеш для нового списка DNS.
- Стартовый журнал показывает MTU TUN и транспорта, источник и список DNS, настройки TCP. DNS-события содержат resolver и длительность. Новые поля не содержат ключей, запросов и URL.

MTU, шифрование, обфускация, Go pipe, QUIC и сервер не меняются. DNS профиля остаётся выбором по умолчанию.

## Экспериментальный приёмный буфер

Реализован вариант RX 512 КиБ при прежнем TX 128 КиБ. Каждый увеличенный сокет занимает разрешение на дополнительные 384 КиБ из общего бюджета 64 МиБ на сессию. При исчерпании бюджета используется RX 128 КиБ. Разрешение освобождается при закрытии и отмене, включая отмену ожидающего подключения.

**В основной пакет увеличение не принято.** На стенде RTT 100 мс без потерь одна загрузка 64 МиБ сократилась примерно с 61 до 16 с, однако последующий сценарий замедленного читателя вызвал воспроизводимую панику smoltcp 0.12.0: `attempt to subtract sequence numbers with underflow`. Короткий повтор с 512 КиБ подтвердил проблему; стек указывает на `Socket::last_scaled_window` → `window_to_update` → `dispatch` в исходящем TCP-участке. Условие отсутствия новых ошибок не выполнено; единичный выигрыш не считается принятым результатом.

Сохранены исходные неуспешные измерения: `verification-publish/awg-stage2-receive-gate.log`, частичный JSON и `awg-stage2-receive-backtrace.log`. Расширенный буфер доступен только внутреннему тестовому стенду; основное состояние и IPC не включают экспериментальный переключатель.

## CUBIC и локальный TUN

Добавлена поддержка CUBIC для отдельного эксперимента отправителя. Из-за объединения Cargo features конструктор smoltcp мог бы поменять алгоритм всех сокетов. Поэтому netstack-smoltcp 0.2.4 закреплён локально в `ior-core/vendor-netstack`, с исходными лицензиями MIT и Apache-2.0; его listener явно выбирает None. Для исходящих сокетов алгоритм также выбирается явно. Cargo cache не редактировался.

Три повтора, RTT 50 мс, потери 0,5%: медиана отправки 64 МиБ 142,782 с с None и 143,195 с с CUBIC (на 0,289% медленнее). p95 маленьких запросов под нагрузкой: 73,403 и 81,286 мс (+10,74%). Критерии ≥10% улучшения и ≤10% ухудшения p95 не выполнены. **CUBIC не принят**, основной пакет явно выбирает None. Числа: `verification-publish/awg-stage2-cubic-gate.json`, оценка `awg-stage2-cubic-evaluation.json`.

Nagle сравнивался отдельно: три чередующихся повтора по 30 запросов из двух записей по 4 байта с промежутком 5 мс, RTT 50 мс без потерь. Медиана 148,873 → 80,775 мс, p95 167,083 → 97,660 мс. Число исходящих pipe-пакетов на 30 запросов одинаковое — 61 в каждом повторе. Это локальное подтверждение уменьшения задержки конкретного типа запросов, не процент ускорения страниц. При первых загрузках 64 МиБ на RTT 100 мс значения Nagle on/off были 61,427/61,368 с; эффект на длительную передачу в этом одиночном сравнении не установлен. Проверялась целостность данных.

## Устройство стенда

`ior-core/crates/ior-core/src/awg_tcp_lab.rs`: два официальных AWG-адаптера, синтетические ключи, loopback IPv6 endpoint, без Wintun, системных маршрутов и внешних сайтов. Задержка применяется к зашифрованным UDP-пакетам в обе стороны; очередь задержки сохраняет порядок. Потери — каждый N-й пакет отдельно в каждой стороне: N=200 для 0,5%, N=100 для 1%. Это воспроизводимая периодическая модель, не модель всех реальных сетей.

Проверяется каждый байт известного шаблона; отдельные сценарии — маленькие запросы, отправка и загрузка, параллельные потоки, задержка читателя и half-close. Запуск AWG и первый handshake прогреваются до замера. Реальный RTT включает таймеры Windows и обработку адаптеров, поэтому может превышать заданные 50/100/200 мс.

Для узких критериев объёмы указаны отдельно: `gate=receive` измеряет загрузку 64 МиБ, остальные передачи по 1 МиБ; `gate=cubic` измеряет отправку 64 МиБ, остальные передачи по 1 МиБ. Полный режим без `gate` использует 64 МиБ в каждой передаче. Критерии сравниваются с вариантом Nagle off / RX 128 КиБ / None, чтобы отделить эффект каждого изменения.

Выполненная функциональная матрица основного кандидата: все девять сочетаний RTT 50/100/200 мс и потерь 0/0,5/1%, по одному проходу, передачи по 1 МиБ во всех сценариях. Все прошли. Отдельный полный проход при RTT 50 мс без заданных потерь использовал 64 МиБ для каждой передачи: загрузка 34,274 с, отправка 53,193 с, две параллельные загрузки по 34,600 с, замедленный читатель 35,005 с. Каждый байт совпал с шаблоном. Это проверка длительной передачи, **не сравнение скорости с контрольным пакетом**. 64 МиБ не прогонялись во всех девяти сочетаниях; увеличение RX и CUBIC уже отклонены собственными критериями. Файлы: `verification-publish/awg-stage2-candidate-matrix.json`, `awg-stage2-candidate-long.json`. Событий `TUNNEL_QUEUE_DROPS` в успешных прогонах нет; задержка очереди при замедлении читателя допустима и не считается ошибкой.

## Ручное сравнение

1. Отключить VPN и полностью закрыть ior, включая трей, перед сменой пакета. Пакеты используют одно сохранённое состояние; запускать один за раз.
2. Сначала оставить «Из профиля». Тот же AWG-профиль, сервер, ior-core, TUN, сеть, браузер, DoH и качество видео для обоих пакетов. Обновление 3x-ui считать изменением условий; старые и новые условия не смешивать.
3. По пять повторов на контрольном и новом пакете, чередуя их. Использовать одни и те же Telegram Web, страницу YouTube, изображения и одно видео с фиксированным качеством.
4. Отдельно записать первый и повторный заход, время до видимого содержимого/изображений, первого кадра, реакции на перемотку и число остановок за две минуты. Первый заход не гарантирует холодный DNS-кеш.
5. После этого на новом пакете отдельно сравнить DNS профиля с Google + Cloudflare. При смене DNS создаётся новое подключение; не смешивать эффект DNS и TCP.
6. Пинг измерять к одному адресу одним методом и при одинаковой нагрузке, отдельно от загрузки. Прилагать лог с временем действия, вариант пакета и DNS.

Если улучшение не повторяется, статус остаётся «ускорение не подтверждено». Автоматизация Firefox при действующей блокировке URL policy не используется.
