# AWG: системный TCP и IPv4-only профиль, 5 октября 2026

Статус: экспериментальная реализация для ручного сравнения. Ускорение
YouTube, Telegram и других сайтов пока не подтверждено. Проверка настоящего
TCP Windows не выполнена: Windows сообщила об отмене запроса UAC.

## Архитектура и изменения

Официальный AWG backend уже подключён: версия `3.1.20260828`, закреплённая
в `ior-core/adapters/amneziawg/go.mod`. Его шифрование, обфускация и обработка
UDP остаются официальными; Rust управляет TUN, маршрутизацией, преобразованием
адресов, приватным IPC, диагностикой и завершением. Полное переписывание
криптографического движка на Rust в эту итерацию не входит.

Официальные клиенты подключают системный TUN к AWG:
[Android](https://github.com/amnezia-vpn/amneziawg-android/blob/master/tunnel/tools/libwg-go/api-android.go),
[Windows](https://github.com/amnezia-vpn/amneziawg-windows/blob/master/tunnel/service.go).
Адаптер ior уже использует официальный `conn.NewDefaultBind` и привязку
внешнего сокета к физическому интерфейсу. У официального Windows
[WinRingBind](https://github.com/amnezia-vpn/amneziawg-go/blob/master/conn/bind_windows.go)
`BatchSize()` также равен 1; произвольного ожидания накопления пакетов не добавляли.

Предыдущий эксперимент сохранял TCP Windows только для IPv4 и включался
файлом `awg-raw-tcp.enabled` в отдельном пакете. Последний пользовательский
фрагмент журнала не содержит событий нового пути, поэтому его фактическое
использование по тому журналу не подтверждено.

В этой итерации:

- Для AWG с комплектным ядром флаг пакетного пути передаётся автоматически.
  Для пользовательского внешнего ядра сохраняется прежний путь: совместимость
  неизвестного бинарника с новым контрактом не предполагается.
- IPv4 TCP с безопасным решением PROXY сохраняет последовательности, окна,
  ACK, SACK, timestamps, данные и завершение Windows; второе TCP-соединение
  smoltcp не создаётся.
- Добавлено преобразование IPv6 TCP в IPv4 для IPv4-only AWG. Оно допускается
  только при однозначном имени из наблюдаемого DNS и существующем, неистёкшем
  A-адресе этого имени. Правила для исходного IPv6 и выбранного IPv4 должны
  независимо разрешать пакетный PROXY-путь; AllowedIPs проверяется транспортом.
  Новый DNS-запрос не блокирует чтение TUN. При отсутствии подходящего адреса
  сохраняется прежний путь с диагностикой причины.
- Нормализация поддерживаемых IPv6 extension headers и сборка фрагментов
  используют существующие ограничения: 64 группы, 1 МиБ, срок 5 секунд.
  Опции, требующие отбрасывания, активная маршрутизация и IPsec не обходятся.
- Контрольная сумма TCP меняется по разнице псевдозаголовков, без второго
  прохода по данным. Повреждённая исходная сумма не исправляется случайно.
  UDP/QUIC этим TCP-преобразованием не затрагиваются.
- ICMPv4 ошибки переводятся в ICMPv6 с ограничением полного ответа 1280
  байт и сохранением заявленной длины цитируемого пакета. Для IPv4-пути ниже
  минимального MTU IPv6 применяется существующий PMTU-кеш и фрагментация IPv4.
  Частичная цитата не получает выдуманную TCP checksum. Это узкий преобразователь
  соединений, а не полноценный NAT64-шлюз; ориентир —
  [RFC 7915](https://www.rfc-editor.org/rfc/rfc7915.html).
- Добавлены события запроса/включения режима, выбора IPv4 и причин перехода
  на прежний путь. Количество активных потоков ограничено 24; исходные очереди
  и ограничения памяти сохранены. При исчерпании лимита новое соединение
  закрепляется за прежним путём, а существующее не переключается между стеками.

DNS-ответы и HTTPS/SVCB hints не переписываются. DoH и старый кеш браузера
без наблюдаемой DNS-связи могут по-прежнему приводить к использованию старого
пути. Правила, требующие неизвестного TLS-имени для выбора DIRECT/REJECT,
также сохраняют прежний путь. Нативный IPv6 через dual-stack AWG остаётся
на прежнем пути. Сервер, ключи, MTU профиля и его DNS не менялись.

## Проверки

Итоговые результаты и контрольные суммы находятся в
`verification-publish/20261005-awg-windows-tcp-stage6/build-result.json`.
Rust-проверки покрывают преобразование TCP/ICMP, фрагменты, истечение DNS,
приоритет маршрутов, лимит потоков, отмену и освобождение ресурсов.
Включён официальный AWG-адаптер; отдельный изолированный стенд проверяет
64 МиБ в обеих семьях адресов с медленным читателем, маленькие запросы и отмену.
Дополнительные случаи используют искусственные RTT 100/200 мс и потери
1%/0,5% с фиксированной последовательностью. TCP-пиры этого стенда — smoltcp;
проценты ускорения Windows или YouTube из этих проверок не выводятся.

В первом расширении комбинированного теста перевод 64 МиБ прошёл, но
последующая IPv6 DNS-проба при reconnect завершилась тайм-аутом. Подробности
сохранены в `awg-real-engine-test.log`. Проверку перевода выделили в отдельный
fixture; исходный reconnect-сценарий и новая отдельная проверка прошли в
итоговом полном прогоне. Возможный фактор — несколько одновременно живых
клиентских сессий с одинаковыми ключами в прежнем fixture; это предположение,
а не установленная причина конкретного тайм-аута.

Добавлен отдельный opt-in тест `windows_tcp_through_production_tun_and_official_awg`:
настоящий Windows TcpStream, рабочий TUN reader/writer, официальный AWG,
64 МиБ, штатная очистка. Он создаёт собственный `ior-native-lab-*` адаптер
и только маршруты `10.7.0.1/32` и `fd00:7::1/128`; физические интерфейсы,
глобальный IPv6, DNS и сервер не изменяет. Запуск требует администратора;
скрипт — `scripts/Invoke-AwgWindowsTcpLab.ps1`. Запрос UAC был отменён,
поэтому реальная передача и откат этого теста **не подтверждены**.
Повторный запрос UAC автоматически не выполнялся.

## Ручное сравнение

Контроль: `20261005-awg-native-tcp-stage5/windows-11/ior.exe`.
Кандидат: `20261005-awg-windows-tcp-stage6/windows-11/ior.exe`.
Старые пакеты сохранены. `dist.bat` не запускался.

С одинаковым профилем, DNS, роутером и состоянием сервера выполнить по пять
повторов на каждом пакете: Telegram Web, одна страница YouTube, одно видео
с фиксированным качеством 4K, одинаковая перемотка и скорость 2×. Первый
заход и повторный учитывать отдельно. Записать время первого кадра,
остановки и запас буфера через «Статистика для сисадминов». Пинг сравнивать
к одному адресу одним способом, отдельно от загрузки.

Если телефон и ПК используют один и тот же клиентский конфиг, на время
проверки ПК отключить VPN на телефоне. В официальном
[AWG receive.go](https://github.com/amnezia-vpn/amneziawg-go/blob/master/device/receive.go)
адрес peer обновляется по аутентифицированным пакетам; два активных клиента
с одним ключом могут перетягивать этот адрес между собой. Это возможный
фактор для проверки, а не диагноз пользовательской проблемы.

В журнале кандидата проверить `NATIVE_AWG_PACKET_PATH_REQUESTED`,
`AWG_RAW_TCP_ENABLED`, `AWG_RAW_TCP_ADMITTED`, а для перевода IPv6 —
`AWG_RAW_TCP_TRANSLATED`. События `AWG_RAW_TCP_FALLBACK*` объясняют,
почему конкретное соединение использовало прежний стек. В HTTP/3 остаётся
существующий UDP-путь; обфускация AWG под QUIC не означает использование h3.

Если улучшение не повторяется, статус остаётся «ускорение не подтверждено».
При регрессии закрыть кандидат и использовать сохранённый контрольный пакет.
Автоматизация Firefox при действующей блокировке URL policy не использовалась.
